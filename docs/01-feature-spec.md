# 01. UI 기반 기능 명세서

> 상태: **설계 검토용 초안 (v0.1)** · 구현 전
> 근거 자료: UI 디자인 8개 화면, IA 표(회원/편지 5개 기능), API 명세서 캡처(13개)
> 기존 코드: 없음 (신규 프로젝트, Node.js + Express + PostgreSQL)

표기 규칙
- **[IA]** IA 표에 근거가 있음 · **[API]** API 명세서에 근거가 있음 · **[UI]** 화면에만 있음
- **[가정 A-n]** 근거 자료가 서로 다르거나 비어 있어서 내가 정한 것. 맨 아래 "가정 목록"에 이유를 적었다.

---

## 공통 규칙

- 모든 날짜 판단(공개일, D-day, 답장 가능일)은 **한국 시간(Asia/Seoul)** 기준이다. [가정 A-7]
- 편지는 **공개 시각 = 공개일 00:00 (KST)** 에 열린다.
- 공개 전 편지는 받는 사람이든 쓴 사람이든 **서버가 제목, 본문, 이미지를 응답에 넣지 않는다.** 수신함의 블러는 프론트가 빈 자리를 꾸미는 효과일 뿐이다.
- 로그인한 사용자 식별은 서버가 발급한 토큰으로만 한다. 프론트가 보낸 사용자 ID, 공개 여부, D-day 값은 쓰지 않는다.

## 01 로그인

| 항목 | 내용 |
|---|---|
| 목적 | 카카오 계정으로 서비스에 들어온다 [UI][IA: 소셜 로그인] |
| 행동 | "카카오로 시작하기" 버튼 |
| 흐름 | ① 프론트가 카카오 인가 페이지로 이동 → ② 카카오가 `redirect_uri`(프론트)로 `code` 전달 → ③ 프론트가 `code`를 백엔드에 전송 → ④ 백엔드가 카카오에서 토큰·사용자 ID 조회 → ⑤ 가입된 사용자면 액세스 토큰 발급, 아니면 가입용 임시 토큰 발급 |
| 표시 데이터 | 없음 |
| API | `POST /api/auth/kakao` [API: 로그인] |
| 연결 | 기존 회원 → 03 홈 / 신규 → 02 회원가입 |

## 02 회원가입

| 항목 | 내용 |
|---|---|
| 목적 | 카카오 연결 후 서비스 이용에 필요한 정보를 받는다 |
| 입력 | 이름, 나이, 성별(여성/남성/비공개), 이메일 [IA], **아이디** [가정 A-4], 약관 동의 [IA: 완료 기준 "모두 동의"] |
| 버튼 | "인증코드 받기", 인증코드 "확인", "짬처리 시작하기" |
| 규칙 | 인증코드 유효시간 5분(UI 04:59), 이메일 인증을 마쳐야 가입 가능, 필수 약관 2개 동의 필수, 알림 수신은 선택 |
| 흐름 | 인증코드 발송 → 코드 확인 → 가입 요청 시 사용자 생성과 인증 기록 사용 처리를 **한 트랜잭션**으로 |
| API | `POST /api/auth/email-verifications`, `POST /api/auth/email-verifications/confirm`, `POST /api/auth/signup` [API: 회원가입, 이메일 인증 코드 발송/확인] |
| 연결 | 가입 완료 → 03 홈 |

## 03 홈

| 항목 | 내용 |
|---|---|
| 목적 | 아직 열리지 않은 받은 편지를 한눈에 본다 |
| 표시 데이터 | 공개 예정 편지 수, 가장 먼저 열리는 편지(D-day, 공개일, 보낸 사람), 공개 예정 편지 목록(D-day, 보낸 사람), 안 읽은 알림 수 |
| 행동 | 분류 탭(전체/나에게서/친구에게서/아무나), 편지 타일 → 수신함, "짬 하나 더 넘기기" → 편지 쓰기, 알림 아이콘 → 알림 |
| API | `GET /api/letters/received?box=sealed` (목록·개수), `GET /api/notifications` (안 읽은 수) [API: 내 편지함 조회] |
| 비고 | "가장 먼저 열리는 편지"는 공개 예정 목록을 공개일 오름차순으로 받은 첫 항목이다. 별도 API는 만들지 않는다. |

## 04 수신함

| 항목 | 내용 |
|---|---|
| 목적 | 받은 편지를 공개 예정 / 열람 가능으로 나눠 본다 [IA: 편지를 받는다] |
| 표시 데이터 | 보낸 사람, 공개일, D-day, 상태. **공개 전 편지는 본문 없음** |
| 행동 | 탭 전환, 열람 가능한 편지 "열어보기" → 05 |
| API | `GET /api/letters/received?box=sealed` / `?box=opened` |
| 범위 밖 | "보낸 사람까지 블러(PLUS)" 배너 — 결제 기능이 없어서 이번 범위에서 제외 [가정 A-8] |

## 05 편지 열람 · 답장

| 항목 | 내용 |
|---|---|
| 목적 | 공개된 편지를 읽고, 공개 당일에만 답장한다 [IA: 편지를 읽는다, 편지 답장] |
| 표시 데이터 | 받는 사람 표기, 제목, 본문, 첨부 이미지, 작성일, 공개일, 보낸 사람, 답장 가능 여부와 마감 시각 |
| 버튼 | 답장(→ 06, 답장 모드), 보관, 삭제, 닫기 [IA 완료 기준: 닫기/답장/보관함] |
| 규칙 | 공개 당일(KST 00:00~23:59)에만 답장 가능, 편지 1통당 답장 1번 [가정 A-5], 처음 열람한 시각 기록 |
| API | `GET /api/letters/:id`, `GET /api/letters/:id/image`, `POST /api/letters/:id/reply`, `PATCH /api/letters/:id/archive`, `DELETE /api/letters/:id/received` [가정 A-1] |

## 06 편지 쓰기

| 항목 | 내용 |
|---|---|
| 목적 | 받는 사람과 공개일을 정해 편지를 봉인한다 [IA: 편지를 보낸다] |
| 입력 | 받는 사람 유형(나/친구/아무나), 받는 사람 아이디(나 제외), 공개일, **제목(1~50자)**, 본문(1~1000자), 이미지(선택) |
| 버튼 | 아이디 "확인", 빠른 기간(1개월/100일/6개월/1년 — 프론트가 날짜로 바꿔 보냄), 임시저장(범위 밖 [가정 A-11]), "봉인하고 보내기" |
| 규칙 | 공개일은 **내일(KST) 이후 ~ 10년 이내** [가정 A-7], "친구"도 아이디로 지정 [가정 A-3], 편지 1통 = 받는 사람 1명 [가정 A-6] |
| 흐름 | 편지 저장 + (나에게가 아니면) 받는 사람에게 "편지 도착" 알림을 **한 트랜잭션**으로 |
| API | `GET /api/users/lookup?handle=`, `POST /api/letters` [API: 편지 작성 및 저장, 편지 수신자 등록 → 통합] |
| 안내 문구 | "공개 전까지는 언제든 수정·삭제할 수 있어요" → `PATCH /api/letters/:id`, `DELETE /api/letters/:id` [API] |

## 07 보관함

| 항목 | 내용 |
|---|---|
| 목적 | 보관한 편지를 다시 본다 |
| 표시 데이터 | 공개일, 보낸 사람, 제목, 본문 앞부분, 답장 여부 |
| 행동 | 검색(보낸 사람 이름·제목·본문), 필터(전체/나에게서/친구에게서/답장함), 카드 → 05 |
| API | `GET /api/letters/received?box=archived&q=&from=` |

## 08 알림

| 항목 | 내용 |
|---|---|
| 목적 | 편지 도착, 봉인 해제, 답장 마감, 답장 도착을 알려준다 |
| 표시 데이터 | 알림 종류, 관련 편지, 보낸 사람, 시각, 읽음 여부, 안 읽은 수 |
| 행동 | 알림 탭 → 관련 화면, "모두 읽음" |
| API | `GET /api/notifications`, `PATCH /api/notifications/:id/read` [API], `PATCH /api/notifications/read-all` [가정 A-10] |
| 생성 시점 | 편지 도착·답장 도착: 편지 저장 트랜잭션 안에서 생성 / 봉인 해제·답장 마감: 별도 스케줄러 없이 **알림·수신함 조회 시 공개 시각이 지난 편지에 대해 생성**(중복은 UNIQUE 제약으로 방지) |
| 범위 밖 | 앱 푸시, 이메일 알림 |

## 가정 목록 (검토 필요)

| ID | 근거 자료 상황 | 내가 정한 것 | 이유 |
|---|---|---|---|
| A-1 | IA·UI에는 "보관함에 넣기 / 삭제"가 있는데 API 명세에 없음 | 보관, 받은 사람 측 삭제 API 2개 추가 | 화면 버튼이 동작하려면 필요 |
| A-2 | 공개 전 수정·삭제 API는 있는데 보낸 편지를 보는 화면이 없음 | `GET /api/letters/sent` 를 **제안 상태**로 명세에만 둠 | 수정·삭제할 편지 ID를 얻을 경로가 없음. 화면이 없으니 구현 여부는 확인 후 결정 |
| A-3 | IA에 친구 명단이 있으나 친구 API 없음 | 친구 기능 제외, "친구"도 아이디로 지정. 유형은 분류 표시용으로만 저장 | 화면/API에 친구 추가·조회 흐름이 없음 |
| A-4 | "아무나"는 아이디로 보내는데 가입 필드에 아이디가 없음 | 가입 시 아이디(영문 소문자·숫자·밑줄 3~20자, 중복 불가) 입력 | 받는 사람을 특정할 수단이 필요. 이메일을 노출하지 않기 위해 |
| A-5 | IA: "비공개 처리됐을 때나 열람한 당일" 답장 가능 | **공개 당일에만** 답장, 1통당 1번 | 내용을 못 읽은 상태의 답장은 UI 흐름(열람 화면에서 답장)과 맞지 않음 |
| A-6 | API에 "편지 수신자 등록"이 따로 있음 | 1통 = 1명, 작성 시 함께 지정 | 화면에서 여러 명을 고르는 UI가 없음. 작성과 지정을 나누면 수신자 없는 편지가 생길 수 있음 |
| A-7 | 시간대·공개일 범위 미정 | KST 00:00 공개, 내일 ~ 10년 이내 | 서비스 사용자가 한국 기준. 상한은 오입력 방지용 |
| A-8 | IA: 보낸 사람 블러는 유료 | 이번 범위 제외 | 결제 기능 없음 |
| A-9 | 이미지 저장 위치 미정 | 서버 로컬 디스크(`UPLOAD_DIR`), 5MB, jpeg/png/webp, **권한 확인 API로만** 제공 | 외부 저장소 계정 정보가 없음. 공개 전 이미지가 URL로 새지 않게 |
| A-10 | API에 알림 단건 읽음만 있음 | 전체 읽음 API 추가 | UI "모두 읽음" 버튼 |
| A-11 | UI에 "임시저장" 버튼 | 범위 제외 | IA·API에 근거 없음 |
| A-12 | IA: "읽은 편지들은 보관함에 저장된다" vs "보관함에 넣거나 삭제할 수 있다" | 사용자가 직접 보관 | 자동 보관이면 "보관" 버튼과 "보관만 함" 상태가 의미 없음 |
| A-13 | 쓴 사람이 공개 전에 자기 편지 내용을 볼 수 있는지 (요청서: "권한이 있는 사용자라도 공개 전 내용 확인 불가", UI: "쓴 나도 못 봐요") | 쓴 사람도 볼 수 없음. 공개 전 수정은 **공개일 변경, 본문·이미지 새로 쓰기(덮어쓰기)** 만 가능 | 요청서 규칙을 그대로 따르면 기존 내용을 불러와 고치는 방식은 불가능함. 친구에게 보낸 편지는 쓴 사람이 볼 수 있게 할지 확인 필요 |
| A-14 | 요청으로 편지 제목(`title`) 추가. 필수 여부, 길이, 공개 전 노출 여부는 정해지지 않음 | 필수, 앞뒤 공백 제거 후 1~50자, **공개 전에는 본문처럼 숨김** | 제목만으로도 내용이 짐작될 수 있어서 "공개 전 내용 접근 제한" 규칙에 포함함. 수신함에 제목을 미리 보여주고 싶다면 이 규칙을 바꿔야 함 |
